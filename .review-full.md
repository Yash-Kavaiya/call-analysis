# Full-project review — call-analysis-project

Reviewed the live application (not a git diff): `src/call_analysis/api/app.py`, config/database/models/auth/storage/schemas/tasks/celery, pipeline + orchestrator, dashboard (`web/app.js`, `index.html`), Docker/compose, packaging, and `tests/*`.

Line numbers refer to the files as they exist on disk at review time.

## Summary

The dashboard happy path is a **local JSON `CallStore` + in-process thread pool**, not the PostgreSQL / JWT / Celery stack advertised in the README and `docker-compose.yml`. The UI and the live FastAPI routes match each other (no JWT), so a single-process `python -m call_analysis.serve` can list, upload, and analyze calls. The “production” layer is a second, disconnected codebase: `auth.py`, ORM models, Alembic, and Celery `process_call` are not wired into `api/app.py`, and they cannot consume the 12-character file-store IDs the API actually writes. This is a capable demo, not a production-ready multi-tenant platform.

## Deploy blockers

These prevent a documented start or an end-to-end analyze when following README / Docker.

1. **Empty `AUTH_SECRET_KEY` crashes process startup even though the live API never uses JWT.**  
   `docker-compose.yml:56` sets `AUTH_SECRET_KEY=${AUTH_SECRET_KEY}`. If the host var is unset, Compose injects an empty string. `AuthSettings.validate_secret_key` (`config.py:167-170`) rejects keys shorter than 32 characters. `get_settings()` is called at import in `api/app.py:36` and `serve.py:20`, so the API container never binds `:8787`. The live routes do not read `settings.auth` at all.

2. **Documented Celery worker cannot start or analyze API jobs.**  
   - `tasks.py:14-16` imports `database.py` at module load. `database.py:22-31` builds `postgresql+asyncpg://…` but **`asyncpg` is not in `requirements.txt` / `pyproject.toml`**. `database.py:34-43` then calls `create_async_engine()` on the **sync** URL `postgresql+psycopg://…`, which SQLAlchemy rejects (async engine requires an async dialect).  
   - `celery_app.py:121` auto-imports `tasks`, so `call-worker` dies on import.  
   - Even if the worker started, `process_call` does `UUID(call_id)` (`tasks.py:37`) and `select(CallRecordModel)` (`tasks.py:47-53`). `CallStore.new_id()` returns `uuid.uuid4().hex[:12]` (`storage.py:39-40`), which is not a valid UUID, and `api/app.py` never inserts a Postgres row. The worker always raises `ValueError` / “Call not found”.  
   - Local `ENVIRONMENT=development` (the default) adds `--reload --autoreload` (`worker.py:33-34`). Celery 5 worker does not accept those flags, so `python -m call_analysis.worker` exits immediately.

3. **Documented DB bootstrap is broken.**  
   - `python -m call_analysis.init_db` imports `database.py` (same asyncpg / sync-URL crash).  
   - `python -m call_analysis.migrate upgrade head` runs `subprocess` with `cwd=__file__` (`migrate.py:20-24`) — a file path, not a directory — and there is **no `alembic.ini`** in the repo.  
   - `alembic/env.py:25` calls `settings.database.url.render_as_string(...)`, but `DatabaseSettings.url` is a plain `str` (`config.py:34-35`), so migrations would `AttributeError` even with a working cwd.

4. **Windows README install of the `prod` extra fails.**  
   README step 2 is `pip install -e ".[prod]"`. `pyproject.toml:101-105` includes `uvloop>=0.21.0`, which does not install on Windows. The dashboard itself only needs `requirements.txt` + an editable install without `[prod]`.

5. **Docker API with `SERVER_WORKERS=4` races the file store.**  
   Compose sets `ENVIRONMENT=production` and `SERVER_WORKERS=4` (`docker-compose.yml:45,59`). `serve.py:39-53` then launches gunicorn with 4 Uvicorn workers. Each worker runs lifespan `recover_interrupted_jobs` (`app.py:129-132`) and submits the same pending IDs to its own `ThreadPoolExecutor`. `CallStore.save` (`storage.py:42-48`) writes JSON with no lock. Duplicate pipelines + torn JSON are likely on any container restart that finds `pending`/`processing` records.

**What does work:** `python -m call_analysis.serve` (default `development`, 1 worker) + dashboard upload/import, if `NVIDIA_API_KEY` is set and ffmpeg + faster-whisper can run. Postgres, Redis, and the Compose `worker`/`beat` services are not on that path.

## Bugs

### Issue 1 -- Severity: bug
- File: `src/call_analysis/api/app.py:80-94` vs `src/call_analysis/tasks.py:27-53` vs `src/call_analysis/storage.py:39-40`
- Description: Dual storage is not dual-write. The live API persists only JSON via `CallStore` and analyzes via `_executor.submit(_run_pipeline)`. Celery `process_call` looks up `CallRecordModel` by `UUID(call_id)` and never sees those records. Compose still runs a worker that cannot process anything the API queues (the API does not call `process_call.delay` at all).
- Suggestion: Pick one backend. Either delete Celery from the default compose/README path, or have the API insert a real UUID into Postgres, share `data/` (already volume-mounted), and enqueue `process_call.delay(str(uuid), org_id)`.

### Issue 2 -- Severity: bug
- File: `src/call_analysis/tasks.py:85`
- Description: `call.metadata = result.metadata` writes to SQLAlchemy’s `MetaData` (`DeclarativeBase.metadata`), not the payload column. The ORM field is `call_metadata` (`models.py:170`). Alembic’s `calls.metadata` column (`alembic/versions/001_initial_schema.py:99`) does not match the ORM name either.
- Suggestion: Assign `call.call_metadata = result.metadata` and align the Alembic column name with `call_metadata`.

### Issue 3 -- Severity: bug
- File: `src/call_analysis/tasks.py:41,59,99,110` and `src/call_analysis/redis_client.py:228-250`
- Description: `JobStatusTracker.set_status` is `async def`, but the Celery task calls it without an event loop. That creates un-awaited coroutines (RuntimeWarning) and never updates Redis job state.
- Suggestion: Use a sync Redis client in workers, or `asyncio.run(...)` around tracker calls.

### Issue 4 -- Severity: bug
- File: `src/call_analysis/audio/asr.py:39-40,24-36` vs `src/call_analysis/config.py:112-123`
- Description: ASR ignores `ASRSettings`. Model size is `WHISPER_MODEL` (default `"base"`), device is `CALL_ANALYSIS_DEVICE`. `.env.example` documents `ASR_MODEL_SIZE` / `ASR_DEVICE`, which have no effect. A user who sets `ASR_MODEL_SIZE=large-v3` still runs `base`.
- Suggestion: Read `get_settings().asr.model_size` and `settings.asr.device` in `transcribe_audio` / `_load_model`.

### Issue 5 -- Severity: bug
- File: `src/call_analysis/auth.py:271-295`
- Description: `require_role` is built with `UserRead.model_construct(role="admin")` and then does `r.value`. `UserRead` is a Pydantic model, not an enum — this is `AttributeError` on every admin/analyst check. The live `api/app.py` does not mount these dependencies (so the dashboard is unaffected), but any attempt to enable the documented RBAC routes will 500.
- Suggestion: `require_role(*allowed: UserRole)` and compare `current_user.role` to those enums.

### Issue 6 -- Severity: bug
- File: `src/call_analysis/celery_app.py:125` and `src/call_analysis/database.py:22-43`
- Description: `check_celery_health` annotates `dict[str, Any]` without importing `Any` (harmless because of `from __future__ import annotations`). The real failure is importing `database` from any worker/health helper: missing `asyncpg` plus `create_async_engine(sync_url)`.
- Suggestion: `sync_engine = create_engine(settings.database.url)` (sync `psycopg`); add `asyncpg` if you keep `async_url`, or switch async to `postgresql+psycopg_async`.

### Issue 7 -- Severity: suggestion
- File: `src/call_analysis/api/app.py:186-219`
- Description: `/api/health` always returns `status="ok"` even when NVIDIA is unconfigured and DB/Redis checks failed. Compose healthchecks and operators cannot distinguish a working analyzer from a box that will fail every job.
- Suggestion: Return `degraded`/`error` when `nvidia_key_configured` is false or (in production) when the chosen backend is down.

### Issue 8 -- Severity: suggestion
- File: `src/call_analysis/config.py:238-244` and `.env.example` (`STORAGE_ALLOWED_EXTENSIONS=.m4a,.wav,...`)
- Description: `allowed_extensions` is `set[str]`. A comma-separated env value is not JSON; pydantic-settings will not produce `{".m4a", ".wav", ...}`. Copying `.env.example` can reject every upload (`app.py:293-295`).
- Suggestion: Document a JSON list, or add a validator that splits on commas.

### Issue 9 -- Severity: nit
- File: `src/call_analysis/api/app.py:424-429`
- Description: `create_app(store=)` assigns a process-global `_store`. Tests that import the module-level `app` after another test can leak stores. Fine for serial pytest, fragile if parallelized.
- Suggestion: Attach the store to `app.state` instead of a module global.

## Security

### Issue 1 -- Severity: bug
- File: `src/call_analysis/api/app.py:222-395` and `src/call_analysis/web/app.js:20-31`
- Description: **Auth/dashboard mismatch, resolved the wrong way.** The UI never sends `Authorization` or `X-API-Key`. The live API also requires neither. Every call route is public: list, detail (includes `full_transcript` and `pii_findings`), delete, upload, import, re-analyze, copilot. Compose publishes `8787:8787` (`docker-compose.yml:66-67`) with `SERVER_HOST=0.0.0.0`. `auth.py` (JWT, API keys, RBAC) is unused. README still claims “JWT + API Keys with RBAC”.
- Suggestion: If this is a local demo, bind `127.0.0.1` only and say so. If it is multi-user, mount `get_current_user_or_api_key` on mutating/PII routes, add a login form that stores the bearer token, and do not enable auth-bypass except when `ENVIRONMENT=testing`.

### Issue 2 -- Severity: bug
- File: `src/call_analysis/api/app.py:319-336`
- Description: Unauthenticated `POST /api/calls/import-local` accepts any `body.path` the process can read and copies it into `data/uploads`. Compose bind-mounts `./data:/app/data` (`docker-compose.yml:64-65,108-109`), so a caller can plant server-readable files onto the host. `get_call` then returns `source_path` (`CallRecord.to_dict`, `models.py:396-421`).
- Suggestion: Remove arbitrary-path import from the networked API, or restrict to a configured allow-listed directory after authentication. Keep “import samples” as an internal walk of the recordings folder only.

### Issue 3 -- Severity: bug
- File: `src/call_analysis/api/app.py:186-218` and `src/call_analysis/web/app.js:37-38`
- Description: Unauthenticated `/api/health` returns `api_key_hint` (`key[:6] + "..." + key[-4:]`). The dashboard paints that hint in the status bar. That is enough of a hosted NIM key to leak into screenshots, logs, and any client that can hit the port.
- Suggestion: Stop returning key material. Report only `nvidia_key_configured: true/false`.

### Issue 4 -- Severity: bug
- File: `src/call_analysis/api/app.py:145-150` and `src/call_analysis/pipeline/runner.py:73,91-99`
- Description: FastAPI `/docs`, `/redoc`, and `/openapi.json` stay enabled in `ENVIRONMENT=production`. Combined with no auth, the full attack surface is browsable. The pipeline also persists **unredacted** `full_transcript` plus `pii_findings` in JSON under `data/calls/` and serves both via `GET /api/calls/{id}`. README claims “PII Detection & Redaction” as a privacy control; storage is the opposite.
- Suggestion: Disable OpenAPI in production. Persist scrubbed text for default reads; gate raw transcript behind a privileged role. Encrypt `data/` at rest if it must hold PII.

### Issue 5 -- Severity: suggestion
- File: `src/call_analysis/auth.py:234-249`
- Description: `get_current_user_or_api_key` short-circuits all auth when `settings.is_testing`, returning a new random `organization_id` on every call. Harmless today (unused), dangerous if those routes are remounted with `ENVIRONMENT=testing` in a shared deploy.
- Suggestion: Limit the bypass to pytest (`PYTEST_CURRENT_TEST`) and use a fixed fixture org id.

### Issue 6 -- Severity: suggestion
- File: `docker-compose.yml:13-14,29-30,181-183`
- Description: Postgres and Redis publish host ports; Redis has no password. Grafana defaults to `admin` / `admin` (also documented in README). Fine for a laptop lab; unacceptable if the compose file is the “production” deploy.
- Suggestion: Drop host ports for data stores, require `REDIS_PASSWORD` / a strong `DB_PASSWORD`, and force `GF_SECURITY_ADMIN_PASSWORD`.

## Architecture / production-readiness

This is **not production-ready**, despite `pyproject.toml` (“production ready”), README “Production Features”, and a Compose stack with OTEL/Prometheus/Grafana.

**Two applications share one repo.**

| Path | What actually runs |
|------|-------------------|
| Live API + dashboard | `CallStore` JSON, `ThreadPoolExecutor`, no auth, no rate limit, no org tenancy |
| Advertised production | Postgres + Alembic + JWT/RBAC + Celery queues + Redis job tracker |

`FeatureFlags` (`config.py:268-280`) are never read. `slowapi` is a dependency but not applied in `api/app.py`. Prometheus scrapes `api:8787/metrics` and `worker:8787` (`prometheus.yml:17-33`); the app has **no `/metrics` route** and the worker does not listen on 8787. `opentelemetry-instrumentation-logging` is imported in `telemetry.py:14` but not declared; API startup swallows telemetry failures (`app.py:122-127`), so tracing silently no-ops.

**Auth is optional in the worst sense:** it is absent on the only API the UI uses. There is no register/bootstrap user flow, no refresh endpoint (a refresh token is defined in `schemas.py:435-437` and minted in the unused login sketch, never returned). `require_role` is incorrect even as unused code.

**Config is internally inconsistent.** Nested `BaseSettings` classes work for `DB_*` / `NVIDIA_*` (tests cover that). The running ASR/PII/Celery/OTEL knobs are only half-connected. Default `OTEL_ENABLED=true` points at `localhost:4317` (`config.py:221-225`) for every local `serve`.

**Tests vs claim.** Seven files: NVIDIA config, PII regex, heuristic diarization, NIM request shaping, JSON store round-trip, and five API tests against the file-store app (`test_api.py`). Those API tests match the current `app.py` (`{"calls": []}`, injected `CallStore`, no JWT). There are **no** tests for auth, RBAC, Celery, ORM, Alembic, Docker, or the pipeline. `create_app` is covered; `process_call` (Celery) is not. That is appropriate for a demo, not for a “Beta / production” contact-center product that stores real call audio and PII.

**Honest ship bar:** treat `python -m call_analysis.serve` as a single-user lab UI. Do not expose `:8787` on a network. Do not market JWT, multi-tenancy, or Celery until one storage + one auth + one worker path is actually connected and tested.
